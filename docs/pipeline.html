Tankou · architecture reference

From viewfinder to flashcard

How a photograph of Japanese text becomes an Anki card — where the work happens, what crosses the native-to-web boundary, and what the card builder actually receives.

The pipeline

The flow crosses exactly one architectural boundary, and stays on exactly one camera stream. Both constraints do real work.

Camera preview
Opens on launch — the fast workflow depends on skipping a home screen entirely.
Confirmed boxes
A box is a promise that OCR has read that sentence, so it should not appear on a single lucky frame. Requiring two consecutive recognitions kills the jitter and makes the promise mean something.
Freeze
Takes the current preview frame, not a separate still. One stream means the boxes the user was looking at are exactly the boxes they get.
Tokenise
Normalise every box to 0–1 coordinates here, before several coordinate spaces have a chance to get mixed up.
Word boxes
Drag-selection, selection handles and window.getSelection() come free in a WebView. Rebuilding them natively is weeks of work for a worse result.
Term lookup
Debounce ~250 ms, cancel in-flight requests, cache per term-and-sentence pair. Without this, dragging a selection fires a lookup per character crossed.

One stream, not two

The obvious design captures a high-resolution still on tap and re-runs OCR on it. That breaks the boxes, and it breaks the promise they make.

Re-running OCR on the still avoids the mapping problem but introduces a worse one: the still may segment sentences differently, or miss one the preview caught. A user who tapped capture on three confirmed boxes would get two, and the box would have been a lie.

Freezing the preview frame instead costs resolution and nothing else. Request the highest analysis resolution the device sustains — 1080p is typical, and ample for text at reading distance. When text is genuinely too small, the answer is camera zoom, which is applied before capture and so moves the boxes and the frozen frame together.

Frame pacing

OCR runs slower than frames arrive. What you do with the surplus decides whether the boxes track reality or drift behind it.

The widened payload

Word, sentence and translation are what the user chose. The other five fields are what the pipeline already knew at that moment — and could not cheaply recover afterwards. 

// Emitted when the user commits to a sense.
public sealed record CardRequest(
    string  Sentence,           // final OCR pass — context, and the card back
    string  Surface,            // as it appeared in the frame
    string? DictionaryForm,     // lemma — what the card should actually teach
    string? Reading,            // furigana
    string? PartOfSpeech,
    Range   SpanInSentence,     // char offsets — disambiguates repeats
    string  Translation,        // the sense the user chose
    IReadOnlyList<string> AlternativeSenses);

Why carry all of it

  • The lemma is the card. A frame reading 食べました should produce a card for 食べる. Only the tokeniser knows that, and only while it holds the token.
  • The span disambiguates. If a word appears twice in one sentence, the surface string alone cannot say which occurrence the user tapped. Character offsets can, and they are what lets the card highlight the right one.
  • Recovering later means re-tokenising. Dropping these fields does not save work; it defers the same NMeCab pass to a moment when you also have to re-locate the token.
  • Audio lookup wants the lemma, not the surface. Forvo has a recording for 食べる; it very likely has nothing for 食べました.

The nullable three

DictionaryForm, Reading and PartOfSpeech are nullable on purpose. A manual drag-selection can land on something that is not a token — half a compound, a particle plus a stem — and there is no lemma to report. The card builder needs to handle that case rather than assume the tokeniser always had an answer.
